# تصميم: تأمين الدخول والبيانات عبر Firebase Authentication

**التاريخ:** 2026-09-01
**النطاق:** إزالة نظام PIN المكشوف بالكامل، ومنع أي كتابة غير مصرَّح بها على قاعدة بيانات Firebase الحية، مع إضافة سجل تدقيق (Audit Log) لمطابقة معايير أنظمة إدارة الموارد البشرية الاحترافية.

## 1. المشكلة (الوضع الحالي)

- `fetchCloudData()` يُنزّل حزمة `system_bundle.json` كاملة إلى متصفح أي زائر عند فتح الصفحة، قبل أي تسجيل دخول، وتتضمن هذه الحزمة `systemUsersList` بكلمات مرور PIN **بنص صريح**.
- كلمة مرور المدير العليا `1975` مكتوبة حرفياً في كود JavaScript العلني (`isAdminPin`)، في 9 مواضع.
- قواعد Firebase RTDB الحالية تسمح على الأرجح بالقراءة والكتابة العامة الكاملة (`.read/.write: true`) — لا توجد آلية خادم تتحقق من الهوية قبل الكتابة.
- النتيجة: أي زائر لديه رابط الصفحة (أو حتى رابط REST المباشر لقاعدة البيانات، الظاهر في كود المصدر) يستطيع قراءة/تعديل/حذف كامل بيانات الموظفين دون أي تسجيل دخول.

## 2. الهدف

1. عدم إرسال أي كلمة مرور أو معرّف حسّاس إلى المتصفح إطلاقاً.
2. منع أي كتابة على قاعدة البيانات لا تنبع من مستخدم مسجّل دخوله فعلياً عبر Firebase Authentication.
3. الإبقاء على القراءة (تصفح/طباعة) مفتوحة للجميع دون تسجيل دخول (قرار تصميمي متعمَّد، يطابق فلسفة النظام الحالية).
4. إضافة سجل تدقيق (من قام بأي عملية حفظ ومتى) — معيار أساسي في أنظمة HR الاحترافية لضمان قابلية التتبع (Accountability/Traceability)، خاصة أن التعديل بات مرتبطاً بهوية حقيقية بدل PIN مشترك.

## 3. البنية

نستخدم **Firebase Authentication (Email/Password)** كخدمة توثيق، دون إضافة SDK كامل: نتعامل معها عبر **Identity Toolkit REST API** (نفس أسلوب REST المستخدم حالياً لكل نداءات RTDB)، حفاظاً على بساطة الكود القائم.

### 3.1 قواعد Firebase RTDB الجديدة

```json
{
  "rules": {
    "system_bundle": {
      ".read": true,
      ".write": "auth != null && root.child('roles').child(auth.uid).exists()"
    },
    "active_sessions": {
      ".read": true,
      ".write": "auth != null && root.child('roles').child(auth.uid).exists()"
    },
    "backups_history": {
      ".read": "auth != null && root.child('roles').child(auth.uid).child('role').val() === 'admin'",
      ".write": "auth != null && root.child('roles').child(auth.uid).exists()"
    },
    "roles": {
      ".read": "auth != null",
      ".write": "auth != null && root.child('roles').child(auth.uid).child('role').val() === 'admin'"
    },
    "audit_log": {
      ".read": "auth != null && root.child('roles').child(auth.uid).child('role').val() === 'admin'",
      ".write": "auth != null && root.child('roles').child(auth.uid).exists()",
      ".indexOn": "timestamp"
    }
  }
}
```

- **تصحيح ثانٍ (2026-09-02):** كانت `roles` بحالة `.write: false` بينما نافذة إدارة الحسابات (البند 3.2) تكتب عليها — تناقض داخل الوثيقة نفسها كان ينتج فشلاً صامتاً: تظهر رسالة نجاح بينما الدور لا يصل إلى Firebase. الكتابة صارت مسموحة **للمدير وحده** (يتحقق منها الخادم من `roles/{uid}/role`)، وهذا لا يوسّع صلاحيات المدير إذ يملكها أصلاً، بينما تبقى الكتابة ممنوعة على غيره فلا يستطيع أحد منح نفسه دوراً.
- **تصحيح جوهري (2026-09-02):** الشرط ليس `auth != null` بل وجود سجل في `roles` أيضاً. السبب: تفعيل Email/Password يفتح مسار `accounts:signUp` العلني، فأي زائر يملك مفتاح الويب (وهو معرّف عام ظاهر في الكود) يستطيع إنشاء حساب لنفسه عبر `curl` دون المرور بأي واجهة. ادّعاء هذه الوثيقة بأن «غياب واجهة التسجيل الذاتي يمنع ذلك» كان خاطئاً. اشتراط وجود سجل في `roles` — وهي عقدة `.write: false` لا يستطيع التطبيق الكتابة عليها — يغلق هذا المسار نهائياً.
- عقدة `roles/{uid}` تُدار **يدوياً فقط** من لوحة تحكم Firebase أو عبر Firebase Console Rules Playground (لا واجهة كتابة لها من التطبيق) — بديل نظام `systemUsers[].pin`.
- قراءة `backups_history` (اللقطات اليومية الكاملة) و`audit_log` (سجل من عدّل ماذا) مقصورة على من دوره `admin` فقط — تطابقاً مع كون هذه بيانات إدارية حساسة، بخلاف `system_bundle` المفتوح للقراءة العامة بقرار تصميمي متعمَّد.
- **نطاق مقصود:** أي مستخدم مسجّل دخوله (له سجل في `roles`) يمكنه الكتابة في `system_bundle` بأكمله. القيود الدقيقة لكل تبويب (RBAC حسب الصلاحيات: dailyReport/staffMaster/safety/evaluation) تبقى مطبَّقة في واجهة المستخدم كما هي الآن — هذا يغلق الثغرة الكارثية (كتابة عامة من الإنترنت) دون تغيير نموذج RBAC الحالي بين المشغّلين الموثوقين أنفسهم. تحسين القواعد لتكون على مستوى الحقل الواحد يبقى تحسيناً مستقبلياً منفصلاً إن رغب المستخدم لاحقاً.

### 3.2 سجل التدقيق (Audit Log)

عند كل عملية كتابة مؤثرة على `system_bundle` (حفظ بيانات موظف، تعديل حالة يومية، تثبيت وجبة، إدارة مستخدمين)، يُضاف سجل إلى `audit_log` عبر `POST` (push):

```json
{
  "uid": "<firebase uid>",
  "displayName": "<اسم المستخدم من roles>",
  "action": "save_daily_status | edit_staff | shift_anchor_change | ...",
  "timestamp": "<ISO 8601>"
}
```

يُعرض هذا السجل في تبويب "الأرشيف والاستعادة" الحالي (الذي يعرض أصلاً اللقطات اليومية) كقسم إضافي "سجل النشاط" يظهر فقط للمدير.

### 3.3 تدفق تسجيل الدخول

1. شاشة الدخول: حقل بريد إلكتروني + كلمة مرور (بدل اختيار اسم + PIN).
2. `POST https://identitytoolkit.googleapis.com/v1/accounts:signInWithPassword?key=<FIREBASE_WEB_API_KEY>` بالبريد وكلمة المرور.
3. عند النجاح: حفظ `idToken` و`refreshToken` و`localId` (uid) في `safeStorage`.
4. قراءة `roles/{uid}.json?auth=<idToken>` لتحديد الدور والصلاحيات وعرضها بنفس منطق RBAC الحالي.
5. تجديد `idToken` تلقائياً كل 50 دقيقة عبر `securetoken.googleapis.com/v1/token` باستخدام `refreshToken` (صلاحية idToken الافتراضية ساعة واحدة).
6. كل نداء `pushDataToCloud`/كتابة على `system_bundle` أو `audit_log` يُرفق `?auth=<idToken>` الحالي.
7. عند فشل التوكن (منتهي الصلاحية وتعذر التجديد) تُعاد الجلسة لشاشة الدخول تلقائياً.

`FIREBASE_WEB_API_KEY` معرّف عام (وليس سراً) يُنسخ من إعدادات مشروع Firebase — آمن تضمينه في الكود مثل `FIREBASE_DB_URL` الحالي.

### 3.4 التعديلات على الكود (الملفات الثلاثة: `index.html`، `نظام_ادارة_الملاك_v8.5_cloud.html`، `نظام_ادارة_الملاك_v8.5_offline.html`)

- **النسخة الأوفلاين:** لا تحتاج أي من تعديلات المصادقة (هي أصلاً معزولة تماماً عن السحابة حسب القرار 7 في وثيقة التسليم) — يُكتفى بحذف أي أثر لنظام PIN/roles منها إن وُجد، دون إضافة منطق Auth جديد لها.
- **index.html و النسخة السحابية:**
  - حذف `pin` من نموذج بيانات `systemUsers`، وحذف `isAdminPin` وكل استخدامات `'1975'`.
  - استبدال شاشة/نافذة الدخول الحالية بنموذج بريد/كلمة مرور.
  - إضافة دوال: `signIn(email, password)`, `refreshIdToken()`, `signOut()`.
  - تمرير `idToken` الحالي لكل نداءات `pushDataToCloud` والدوال المشابهة (إرفاق `?auth=`).
  - إضافة `logAuditEvent(action)` تُستدعى من نقاط الكتابة الرئيسية.
  - تبسيط `handleOpenUserManagement`: تصبح تعرض/تعدّل الدور المخزَّن في `roles` لِـ uid قائم فقط (لا إنشاء حسابات من الواجهة).
  - قفل الجلسة الفردية (Single Active Session) يصبح مفتاحه `uid` بدل الاسم النصي.

## 4. خطوات النشر (يدوية، تتطلب لوحة تحكم Firebase)

1. تفعيل Firebase Authentication → Email/Password.
2. إنشاء حساب لكل مستخدم حالي في `defaultSystemUsers` (admin + المشغّلين)، بإيميل حقيقي وكلمة مرور قوية.
3. لكل حساب، إضافة `roles/{uid}: {"role": "admin"|"operator", "name": "..."}` يدوياً من تبويب Realtime Database في اللوحة.
4. تحديث Security Rules بالنص في القسم 3.1.
5. الحصول على `FIREBASE_WEB_API_KEY` من Project Settings ووضعه في الكود.
6. نشر تعديلات الكود.
7. اختبار قبول الدخول الصحيح، رفض الدخول الخاطئ، ورفض أي `PUT` مباشر بدون `auth` (عبر curl) بكود 401.

## 5. المخاطر والقيود المقبولة لهذه الجولة

- لا تحقق دقيق للصلاحيات (RBAC) على مستوى قاعدة البيانات لكل تبويب — فقط "مسجّل دخول أم لا". القيد قائم أصلاً بنفس الشكل اليوم (RBAC واجهة فقط)، لذا هذا ليس تراجعاً بل إبقاء على نفس المستوى مع إغلاق الثغرة الأخطر.
- استرجاع كلمة مرور منسي يعتمد على آلية Firebase القياسية (بريد استعادة) — يتطلب أن تكون عناوين البريد المستخدمة حقيقية وقابلة للوصول من قبل كل مستخدم.
- عدد الحسابات محدود جداً (~3-4) فينشأ يدوياً؛ لا حاجة لواجهة تسجيل ذاتي (self-signup) وهذا مقصود أمنياً (يمنع أي زائر من إنشاء حساب لنفسه).
